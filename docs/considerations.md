# Considerations

1. Nested, inconsistent JSON structures. The API returns deeply nested objects (actions have optional committee, sourceSystem, calendarNumber sub-objects that aren't always present). Flattening this into clean relational tables — deciding what becomes a column vs. a separate table — is genuine modeling work, not just a SELECT *.
2. Bill numbering resets every Congress. HR 1 in the 118th Congress is a completely different bill from HR 1 in the 119th. If you naively key on bill number alone, you'll silently merge unrelated bills. Your natural key has to be (congress, billType, billNumber) — a good example of a "looks simple, will burn you" data quality issue to describe in an interview.
3. Action type isn't a clean state machine in practice. I mentioned the finite set of action types (Committee, Floor, BecameLaw, etc.) as a clean signal, but in reality bills can bounce backward — a bill can go back to committee after floor action, get re-referred, or sit in "ResolvingDifferences" for months while also having new committee actions logged. Deriving a single current status field means writing real logic (e.g., "most recent action of certain types wins" with tie-breaking rules), not just taking MAX(action_date). This is a legitimately good dbt model to show off.
4. Cosponsors are not append-only. Cosponsors can withdraw, and the API tracks both current count and total-including-withdrawn separately. If you're not careful, an incremental/upsert model will overstate current support. This is a great real-world lesson in "don't assume your fact table only grows."
5. Missing/sparse data by era. Subject terms are inconsistent pre-1973 through 2008 (Legislative Indexing Vocabulary vs. later CRS terms), and pre-1995 bills have thinner sponsor/cosponsor data. If you scope to recent Congresses only (which I'd recommend anyway), you avoid most of this — but it's worth documenting as a known limitation, which shows scoping judgment.
6. Text fields need real cleaning. Action text fields are free-form legislative language ("Passed Senate without amendment by Yea-Nay Vote. 79 - 19. Record Vote Number: 71."). If you want to extract structured signal from this (e.g., pull out vote counts or record vote numbers), that's a legitimate parsing/regex task — good for showing SQL string manipulation or a light dbt macro.
7. Many-to-many relationships everywhere. Bills-to-subjects, bills-to-committees, bills-to-cosponsors — all many-to-many, which is exactly why the bridge-table pattern I mentioned earlier matters. Handling these correctly (vs. flattening into comma-delimited strings, which is a common junior mistake) is a good signal.
8. Duplicate/near-duplicate legislation. Companion bills (same bill introduced in both chambers) and related bills aren't automatically merged — the API has a relatedBills field, but reconciling "is this really the same policy effort" is a judgment call, not a clean join. You could choose to model this or explicitly scope it out — either is a fine interview answer as long as you can explain the decision.
